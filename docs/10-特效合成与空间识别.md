# 10 · 特效合成与空间识别

这份文档修正 Reelix 的**根本定位**，并立起特效合成里最基础、先前缺失的地基：**识别扫描 3D 空间场景**（相机追踪 / SfM / 三维重建），以及由它派生的一整套能力——**摄像机、视频 2D→3D 空间场景转换、三维文字与三维平面、关键帧**。

> **本文档为 v3，已彻底删除「流体 / 液态 / 溶图」相关内容。** 那是早期把一次语音识别错误（「溶图」）当成需求而写进来的，用户已明确澄清：**Reelix 没有流体/液态这回事。** 详见第〇节。

---

## 〇、先纠正定位（写在最前）

> 用户原话：「**这并不是一个剪辑软件，还是特效合成软件，别忘了！！**所以说特效合成里面的**识别扫描 3D 空间场景**这种最基础的需要有，加入特效合成。」

**Reelix 是特效合成软件。剪辑是它的附属能力，不是它的身份。**

| 项 | 旧写法（作废） | 新写法（以此为准） |
| --- | --- | --- |
| 身份 | 剪辑与特效合体的视频软件 | **特效合成软件**（合成优先，剪辑内建） |
| 主对标 | Premiere Pro | **After Effects / Fusion / Nuke**（合成） |
| 副对标 | — | Premiere Pro（剪辑轨道能力） |
| 体验对标 | — | **Blurrr**：界面**友好亲切、上手即用、极致扁平**（看起来舒服、愿意上手，不是幼稚的"可爱"） |
| 能力标尺 | — | **达芬奇的至少一半**（这是硬目标，见第七节） |
| 第一功能 | 多轨时间线 | **图层合成 + 效果栈 + 空间识别** |
| 剪辑的地位 | 地基 | **附属**：因为做合成必须能摆镜头顺序，所以内置剪辑轨道 |

**对融合模型的直接影响（这是好消息）：** 内部求值确实是一张 DAG（脏标记、反向拉取、线程池调度），但**用户界面始终是图层 + 效果栈**——时间线轨道、图层树、效果栈是同一份数据的不同看法，正好印证「合成是主、剪辑是内置的基础能力」。所以 [docs/04](04-剪辑与特效融合设计.md) 的架构不用推翻，**只需要把叙述重心从「剪辑」倒过来放到「合成」**。

### 「溶图 / 液态 / 流体」的更正（重要）

用户后续澄清：**「流体」「液态」是语音识别错误，Reelix 从来没有这个需求。** 本文档早期版本（v1 / v2）把「溶图」当作液态/流体特效来处理，是**误读，现予彻底作废**。

真正对应「两个东西融到一起」的基础能力，是合成里最标准的**图像融合**：

| 真正的「融合」 | 是什么 | 在哪 |
| --- | --- | --- |
| 图层混合模式 | 正片叠底 / 滤色 / 叠加 / 相加 | 图层的基本能力，见 [docs/02](02-功能规格.md) |
| 遮罩合成 | Alpha / Luma 遮罩、Matte、跟踪遮罩 | 图层 + 三维平面 |
| 蒙版与形状遮罩 | 钢笔遮罩、羽化、扩展 | 图层 |

**结论：** 融合这块**不需要新造效果**，它在图层合成里本就成立。用户真正强调、且必须补齐的地基是**空间识别**（第一、三、4.1 节），以及它的派生产物——**摄像机、2D→3D 转换、关键帧**（4.2、4.3 节）。**流体/液态不再出现在 Reelix 的任何文档、任何里程碑、任何效果清单里。**

## 一、什么叫「识别扫描 3D 空间场景」

它在行业里的名字有三个，说的是同一件事：

| 叫法 | 英文 | 说明 |
| --- | --- | --- |
| 相机追踪 | Camera Tracking / Matchmove | 反推摄像机的运动轨迹 |
| 运动恢复结构 | SfM（Structure-from-Motion） | 从多帧图像同时恢复相机与场景三维结构 |
| 空间扫描 | Scene Reconstruction / MVS | 从相机与图像生成稠密点云/深度，得到场景三维形 |

**它分三步，缺一不可：**

1. **2D 特征点追踪。** 在每一帧里找出稳定、可重复识别的角点/斑块，并在相邻帧之间把它们**匹配**起来，形成一条条"点的时间轨迹"。
2. **相机解算（SfM）。** 用这些轨迹反过来算：摄像机在每一帧的**位置与朝向**（外参）、以及**焦距/畸变**（内参）。这是"扫描"的核心产物。
3. **三维场景。** 有了相机与匹配点，就能三角化出**稀疏点云**；再往下做稠密重建（MVS），得到**深度图/网格**。有了它，才知道"画面里那个墙在空间的哪个位置"。

**为什么说这是特效合成的第一块地基：** 只要你想把**任何三维的东西钉进实拍画面**——贴一个广告牌、在空地上放一个燃烧的卡车、把文字贴在倾斜的墙面上、替换天空还要跟着镜头转——都**必须先知道摄像机怎么动的**。摄像机数据在手，三维元素才会"焊"在画面里；没有它，所有合成都是漂浮的贴纸。

> 用户原话：「**你做特效往 3D 空间场景里放个图片，放个文字，你没有空间识别，你做你大爸？**」——判断完全正确，这就是地基。

## 二、Gaffer 能不能做到？（必须先说清楚）

**不能。这里必须诚实，不能让用户误以为已经解决了。**

| 问题 | 事实 |
| --- | --- |
| Gaffer 是什么？ | **节点式合成与渲染框架**（BSD-3-Clause，C++ / Python，走 VFX Reference Platform） |
| 它含相机追踪 / SfM 吗？ | **不含。** Gaffer 没有内置的解算器，它**消费**别人算好的相机数据 |
| 工业流程里追踪数据从哪来？ | 独立解算器算完之后喂给 Gaffer，常见的是 **3DEqualizer / PFTrack / SynthEyes / Nuke 的 CameraTracker** |

**那 Gaffer 给 Reelix 的价值到底是什么？** 是**模型**，不是功能：

- 延迟求值（Deferred Evaluation）——不主动算，被问才算
- 节点（Node）与类型化插槽（Plug）的结构（**仅用于内部求值引擎，界面不暴露节点**）
- Box / Reference 概念 → Reelix 的复合片段
- 多线程求值调度

这些**已经在 [docs/06](06-参考项目与许可边界.md) 第三节被借鉴了**，也应该继续借鉴。但「识别扫描 3D 空间场景」这件事，Gaffer 提供不了，**必须另找方案**。好消息是：这件事有一个 BSD 许可的成熟答案。

## 三、技术选型：三条路线并用

### 路线 A · COLMAP（主力解算，离线高精度）✅ 推荐

| 项 | 内容 |
| --- | --- |
| 是什么 | **通用 SfM / MVS 管线**，带图形界面与命令行 |
| 许可 | **BSD License（新版 BSD）** ✅ 在 Reelix 白名单内 |
| 提供 | 相机内参 + 每帧外参、稀疏点云、稠密深度图 / 网格 |
| 怎么用 | **作为 sidecar 独立进程**，与 FFmpeg 同一种做法：Reelix 通过 IPC 调它、读它输出的 JSON / PLY，**不把 C++ 源码并进仓库** |
| 为什么走 sidecar | ①它是 C++ + CUDA 的重型工程，并进来会撞体积红线 ②崩溃不拖垮主程序 ③BSD 许可允许随包分发二进制 |

**定位：** 离线、精确、慢。用于"这个镜头我认真追踪一次，然后反复用"的场景。

### 路线 B · 自研交互式追踪（Rust，快解）✅ 必须做

COLMAP 是离线批处理，**它不是交互式的**——用户拖着一个三维元素时，不能每次都等 COLMAP 跑完。所以 Reelix 必须自己有一套**实时的、交互式的**追踪：

| 环节 | 做法 | 许可 |
| --- | --- | --- |
| 2D 特征检测与匹配 | 用 **OpenCV** 的 `features2d`（ORB / AKAZE）+ 光流 | **OpenCV 4.x 是 Apache-2.0** ✅ 可并入 |
| 相机解算 | 五点法 / EPnP 求初始位姿 + **光束法平差（BA）** 精化 | 自研，矩阵用 `nalgebra`（Apache-2.0） |
| 点云 | 匹配点三角化 → 稀疏点云 | 自研 + `nalgebra` |
| 稳定（副产品） | 追踪做完，"反着用"就是视频稳定 | 自研 |

**定位：** 实时、够用、可交互。用户在界面上框一块区域，几秒内看到追踪轨迹与相机预览。

### 路线 C · 三维视图与预览（three.js 侧）

追踪/解算出的**相机关键帧 + 点云** → 转成 three.js 的相机与点云对象 → 在 **[docs/09](09-3D摄像机与素材库.md) 已锁定的 3D 视图**里预览。这条线已经在 [docs/09](09-3D摄像机与素材库.md) 铺好了，**不需要第二套 3D 技术栈**。

### 三者关系

```
实拍视频
   │
   ├─▶ 路线 B（Rust 交互式）：快解 → 立刻可预览、可调整     ← 用户日常用这个
   │
   └─▶ 路线 A（COLMAP sidecar）：精解 → 高精度、可反复用    ← 用户"认真做"时用这个
                  │
                  ▼
        统一的相机数据格式（JSON）
                  │
                  ▼
       路线 C（three.js 3D 视图）预览 + wgpu 管线参与导出
```

**关键约定：A 与 B 输出同一份格式的相机数据，用户可以在两者之间切换，互不锁定。** 格式定义在 `src/types/camera.ts` 与 `src-tauri/src/tracking/model.rs`。

## 四、空间识别派生出的四组核心能力

空间识别不是终点，它是**四组能力的共同地基**。这四组全部命中用户点名的需求。

### 4.1 空间追踪类（特效合成的地基）

| 效果 | 参数 | 说明 |
| --- | --- | --- |
| **特征点追踪** | 追踪区域、特征数量、最小间距、精度（快/标准/精） | 出 2D 轨迹，画面上可见轨迹点与轨迹线 |
| **相机解算** | 求解器（交互式 / COLMAP）、焦距（自动/手动 mm）、畸变、关键帧间隔 | 出相机内外参 + 求解误差（重投影误差，单位像素） |
| **三维场景** | 点云输入、坐标原点、缩放参考（选两条轨迹定尺度） | 场景的三维容器，三维元素都挂在它下面 |
| **三维平面** | 依附平面（选三个轨迹点）、尺寸、朝向 | 贴广告牌、贴屏幕、贴地面 |
| **三维文字** | 文字、字体、挤出厚度、材质色 | 文字跟着镜头走，焊在空间里 |
| **点云** | 输入点云、点大小、着色模式（原色/深度/误差） | 调试与预览用 |

### 4.2 摄像机（三维空间里的眼睛）

摄像机是**空间识别的产物**，也是**用户手动创作的入口**。两种来源并存：

| 来源 | 说明 |
| --- | --- |
| **解算驱动** | 相机追踪算出来的相机，自动生成一条相机关键帧轨道，用户可叠加手动偏移 |
| **手动创建** | 用户在三维视图里直接摆一台摄像机，自己打关键帧运镜 |

参数表与操作方式见 [docs/09](09-3D摄像机与素材库.md)。要点：

- **焦距 / 视场角**：支持 24–200mm 等价的焦距换算，或直接给 FOV
- **景深**：光圈、对焦距离、焦平面（合成时的散焦预览）
- **运动模糊**：快门角度
- **多机位**：一个场景可挂多台相机，时间线上可切换「当前机位」

### 4.3 视频 2D → 3D 空间场景转换（用户点名要的）

这是把一段**平面视频**变成**有深度、可摆三维元素的空间**的过程。它是空间识别的直接应用，用户明确要求。

| 步骤 | 做什么 | 产物 |
| --- | --- | --- |
| 1 · 追踪 | 对视频跑特征追踪 + 相机解算 | 相机轨迹 + 稀疏点云 |
| 2 · 建空间 | 把点云立成「三维场景」，定尺度与地平面 | 一个三维空间容器 |
| 3 · 转换 | 原始视频作为**纹理**贴到一个跟随相机的「背景板」上，或做**深度分层**（前/中/后景分离） | 一个 2D 视频驱动的 3D 场景 |
| 4 · 摆放 | 往空间里放图片、文字、三维平面、模型，它们**跟着镜头一起动** | 合成结果 |

**两种转换模式，用户可选：**

| 模式 | 原理 | 适合 |
| --- | --- | --- |
| **相机反投（Camera Projection）** | 视频贴在相机反投影平面上，三维元素按解算相机摆放，视觉上"焊"在实拍里 | 贴广告牌、贴文字、替换墙面内容 |
| **深度分层（Depth Layering）** | 用深度图把画面切成多层，每层独立位移/模糊，产生视差 | 伪 3D 视差、画面里"抠出"前景 |

> **红线：2D→3D 转换全程是几何与图像处理（追踪 + 反投影 + 深度估计），不接任何 AI 模型、不联网。** 深度估计用传统多视图几何（MVS）或双目/运动视差，不用神经网络，符合产品线"无 AI"的硬约束。

### 4.4 关键帧（没有关键帧的合成软件可以去死了）

> 用户原话：「**你他妈剪辑软件没关键帧能去死了。**」

关键帧是**整个 Reelix 的时间轴骨架**，不是某一个效果的附属功能。它必须满足：

| 能力 | 要求 |
| --- | --- |
| **任意参数可打帧** | 图层的位置、旋转、缩放、锚点、不透明度、每个效果的每个参数，都能打关键帧 |
| **曲线编辑器** | 不只是线性，要有**贝塞尔手柄**、缓入缓出、定格、匀速，可框选批量调整 |
| **插值模式** | 线性 / 贝塞尔 / 定格（Hold）/ 缓动预设；可对整条曲线设默认 |
| **时间轴可视化** | 关键帧在时间线上以小菱形显示，可拖拽、可复制、可框选移动、可整体缩放（时间重映射） |
| **共享引擎** | 时间线、图层树、效果栈、摄像机、三维元素**共用同一套关键帧引擎**，不允许各做各的 |
| **打帧手感** | 一键「在当前时间打帧」，参数变化时**自动进入打帧状态**（可关），带明显视觉反馈 |

关键帧数据模型见 [docs/04](04-剪辑与特效融合设计.md)，界面呈现见 [docs/05](05-界面规范.md)。

## 六、预设特效与素材文件夹结构（用户点名要的）

> 用户原话：「**要有预设的特效，并且还要有清晰易懂的文件夹，就是在里头的文件夹里面，有个根目录叫上传素材，点进去之后就会有几个，比如说音效、音乐、图像，工程等等，这样子进入软件之后，它就会出现在预设里面。**」

### 6.1 素材文件夹结构（"上传素材"根目录）

软件首次启动时，在用户数据目录下自动创建这棵**固定的、清晰易懂**的目录树：

```
上传素材/                    ← 根目录（用户往这里丢东西）
├── 音效/                    ← 短音效（打击、转场、环境声）
├── 音乐/                    ← 背景音乐、BGM
├── 图像/                    ← 图片、贴图、Logo
├── 视频/                    ← 实拍素材、素材库视频
├── 字体/                    ← 用户自带字体（内容层用）
├── 预设/                    ← 用户保存的预设特效、预设动画、预设调色
└── 工程/                    ← 工程模板、可复用的复合片段工程
```

**规则：**

- 这棵树**用户可见、可改**，就是一个普通的磁盘文件夹，不是软件私有的黑盒。
- 用户在资源管理器里往里丢文件，**软件里"素材箱"自动刷新**并显示。
- 每类素材在软件内有对应的默认归类，但用户可以把任何文件放进任何子目录，软件按**实际所在目录**归类，不强制。
- 用户可在设置里**更改"上传素材"根目录的位置**（比如放到 D 盘），软件记住路径。

### 6.2 预设（Presets）

**预设 = 可复用的"效果 + 参数 + 关键帧"打包。** 分三类：

| 类型 | 是什么 | 存哪 |
| --- | --- | --- |
| **效果预设** | 一组效果栈 + 参数值，套到任意图层上 | `上传素材/预设/` |
| **动画预设** | 一段关键帧动画（如"弹入""浮动""打字机"） | `上传素材/预设/` |
| **调色预设** | 一组颜色效果（LUT + 参数） | `上传素材/预设/` |

**关键行为：**

- 用户在任意图层上调好效果后，点「保存为预设」→ 存进 `上传素材/预设/`。
- 预设保存后，**立刻出现在软件左侧「预设」面板里**，可搜索、可拖拽套用、可右键重命名/删除。
- 预设面板与素材箱**共享同一套文件夹浏览逻辑**：进入软件就能看到"上传素材"及其子目录，点子目录就能看到里面的东西。
- 预设支持**文件夹分组**（用户可在 `预设/` 下再建子目录）。

### 6.3 素材箱（素材管理界面）

| 能力 | 要求 |
| --- | --- |
| **视图切换** | 列表 / 网格（缩略图）两种，一键切换 |
| **文件夹树** | 左侧显示"上传素材"及其子目录，可展开折叠 |
| **排序 / 搜索** | 按名称、日期、类型、时长排序；支持中文与拼音首字母搜索 |
| **拖拽** | 从素材箱拖到时间线或图层树，直接成为片段/图层 |
| **导入** | 支持拖入外部文件、系统文件对话框导入、复制到"上传素材"对应目录 |
| **缩略图** | 视频/图片自动生成缩略图并缓存 |

## 七、能力标尺：达芬奇的至少一半

> 用户原话：「**最终目标虽然达不到达芬奇，但肯定得达到达芬奇至少一半。**」

这不是一句口号，是**可检查的标尺**。下表是"一半"的具体落点（打勾=首版要具备，否则谈不上"一半"）：

| 维度 | 达芬奇有什么 | Reelix 的"一半"（首版目标） |
| --- | --- | --- |
| 剪辑 | 多轨、修剪、切割、变速、多机位 | ✅ 多轨 + 修剪 + 切割 + 变速；多机位（基础） |
| 调色 | 节点调色、色轮、限定器、跟踪窗口 | ✅ 基础调色（色轮 + LUT + 曲线），跟踪窗口用空间追踪的 2D 轨迹 |
| 合成 | Fusion 节点合成 | ✅ 图层 + 效果栈 + 关键帧（界面不暴露节点） |
| 空间 | 3D 摄像机追踪、平面追踪 | ✅ 相机解算 + 三维平面/文字 + 2D→3D 转换 |
| 音频 | 多轨、混音、降噪 | ✅ 多轨音频 + 音量/淡入淡出 + 波形 |
| 交付 | 多格式导出、HDR | ✅ H.264/HEVC/ProRes 导出，1080p/4K |
| 素材管理 | 媒体池、元数据、智能箱 | ✅ 素材箱 + 文件夹树 + 预设（本文件第六节） |

**明确达不到的（诚实说）：** HDR 全流程、杜比视界、云端协作、AI 功能、专业音频后期、分布式渲染。这些**不做，也不假装做**。

## 八、落地顺序

| 阶段 | 做什么 | 为什么这个顺序 |
| --- | --- | --- |
| **M1（剪辑基础）** | 时间线可编辑（修剪/拖拽/切割/多轨/撤销重做）、预览可播放、音频波形、**录音** | 合成要有素材可摆，先把附属能力打通 |
| **M2（合成基础 + 关键帧 + 必备特效）** | 图层 + 效果栈能开能连能实时预览；**关键帧引擎与曲线编辑器**（4.4）；**移动/旋转/缩放/锚点/不透明度**；基础融合（混合模式/遮罩）；**蒙版**、**色度抠图**、**粒子系统** | 关键帧是骨架，必备特效一样不能少，必须先立 |
| **M3（融合 + 预设 + 复合片段）** | 时间线与图层树双向联动、共享关键帧引擎、**复合片段（预合成）**、**预设特效与素材文件夹结构**（第六节）、**2D 特征点追踪与视频稳定** | 追踪是空间识别的前半程，先上；预设与复合片段是用户点名的基础能力 |
| **M4（交付）** | 导出、打包 MSI、首启向导（含"上传素材"目录创建） | 先能交付，再上重头戏 |
| **M5（空间识别 · 核心）** | **相机解算**（交互式 + COLMAP sidecar）、**三维场景 / 三维平面 / 三维文字**、**摄像机**、**视频 2D→3D 空间场景转换**、点云 | 用户明确点名必须有的地基，独立成一个核心里程碑 |

**M1 之前不要碰导出，M3 之前不要碰相机解算。** 这几件事最容易让人分心然后项目烂尾。

> **注意：** 早期文档里的「M6 流体与稠密重建」**已删除**。稠密重建（MVS）作为空间识别的可选深化，并入 M5 的可选部分，**不再单独设里程碑**。

### M5 的验收（草案）

**M5 · 空间识别**

- [ ] 导入一段有横向摇镜的 1080p 实拍，框选区域后点「开始追踪」，30 秒内出轨迹与相机预览
- [ ] 三维视图里能看到相机运动的轨迹球，与画面运动方向一致
- [ ] 加一个「三维文字」挂在场景里，**播放时文字跟着镜头走，视觉上不漂移**
- [ ] 加一个「三维平面」贴在墙面上，播放时贴合稳定
- [ ] **手动创建一台摄像机**，打关键帧运镜，能在时间线上切换机位
- [ ] **2D→3D 转换**：一段平面视频经"相机反投"模式后，往空间里放的图片/文字跟着镜头一起动
- [ ] 相机解算的重投影误差有可见显示，超过阈值时**明确提示「追踪失败，请重新框选」**
- [ ] COLMAP sidecar 调用成功，输出的相机数据与交互式解算**能互相切换**
- [ ] COLMAP 进程崩溃或被强杀，**主程序不受影响**，只弹中文提示
- [ ] 稳定功能：对一段抖动的素材应用后，画面抖动明显减小，边缘无黑边溢出（或自动裁切）

## 九、红线

1. **3D 视图只作预览。** 导出走 wgpu + WGSL 管线，**禁止 WebGL 截屏导出**。
2. **解算进程必须可隔离。** COLMAP 走 sidecar 独立进程，超时可杀，崩溃不传染主程序。
3. **不引入 GPL。** OpenCV 是 Apache-2.0 可用；3DEqualizer / PFTrack 这类**商业软件只做格式与流程参考，不逆向、不并入**。
4. **相机数据格式必须开放。** 一份 JSON，three.js 与 Rust 两侧共用；用户能导出，也能导入别人的。
5. **不把「追踪」做成 AI 功能。** 全程是几何算法（特征匹配 + 平差），**不接任何模型、不联网**。这符合产品线"无 AI"的红线。
6. **关键帧是骨架，不允许缺失。** 任何可调参数都必须能打关键帧，共用同一引擎。
7. **性能兜底。** 追踪是重活，必须能后台跑、能看进度、能取消。**界面绝不能因为解算而假死。**
8. **体积不变心。** COLMAP sidecar 会占体积，但它属于"可选组件"——首启向导里可以不让装，用户需要空间识别时再装，**主安装包仍守 150MB 红线**（见 [docs/09](09-3D摄像机与素材库.md) 的体积预算表）。
